# 饥荒联机版（DST）核心架构决策、设计思想与源码哲学

> “代码只是结果，设计决策才是灵魂。” 本文档不堆砌具体业务案例，专门剖析饥荒底层引擎架构、顶流 Mod 作者的设计哲学、为什么必须这么设计，以及违背这些设计带来的隐性代价。

---

## 一、 为什么饥荒采用“纯组件化（ECS 变体）”而非传统 OOP 类继承？

### 1. 设计初衷与底层哲学
饥荒几乎所有的实体（Entity）都是由 `CreateEntity()` 创建的一个空壳容器，所有能力全部通过 `inst:AddComponent(...)` 动态组装：
- **为什么不写 `class Monster extends Character`？**
  - **现实维度**：在饥荒世界里，任何事物都具有极高的交叉属性。一头猪（Pigman）既是生物（`health`, `combat`, `locomotor`），又是可交易对象（`trader`），还可以被收买成为随从（`follower`），死后还会掉落肉（`lootdropper`），甚至可能发疯变成疯猪（形态切换）。如果用传统类继承，单继承无法处理网状特征，多重继承则会导致“死亡钻石（Diamond Problem）”。
  - **动态拔插**：组件化允许游戏在运行时动态给实体赋予或剥夺能力。例如：给玩家添加一个“冰冻”能力，只需要临时 `inst:AddComponent("freezable")`，解冻后再移除。

### 2. 这种设计的最大工程好处
- **极端解耦**：每个组件只负责自己的单一职责。`combat` 不关心你的武器是用木头做的还是魔法变的，它只关心武器实体上有没有 `equippable` 和数值接口。
- **Mod 极易介入**：第三方 Mod 无需��构原版的深层类树，只需通过 `AddPrefabPostInit` 拿到 `inst`，随时挂载自己的专属组件或监听组件事件。

## 二、 为什么双端同步必须严格执行“Pristine 物理隔离”？

### 1. 设计初衷与底层哲学
饥荒是主客机对等预测模型（Client-Side Prediction）。客机玩家按下移动或交互键时，客机本地立刻开始播放动作，同时将 RPC 发往服务端。

### 2. 为什么要有 `inst.entity:SetPristine()` 这一道“楚河汉界”？
- **网络实体的两面性**：
  - 客机连接服务器时，客机本地只收到服务器下发的预制体名称和初始 Transform。
  - 客机执行 `Prefab.fn` 初始化时，它只能读取到 `inst.entity:SetPristine()` **之前**声明的物理体、动画状态、网络变量（`net_*`）和 Tags。
  - `SetPristine()` 之后，如果不是主机（`if not TheWorld.ismastersim then return inst end`），客机立即截断退出！
- **为什么这么写？**
  - **内存节约**：客机没有必要、也不应该去加载成百上千行的 AI 寻路、战斗计算、血量逻辑、战利品掉落。客机只需要“画出图像、播放声音、响应按键”。
  - **权限收拢**：判定伤害、扣除饱食度、生成物品必须由服务端权威决策（Server Authoritative），客机绝无权限修改这些数据，杜绝客户端作弊。

## 三、 为什么事件驱动（Event-Driven）优于每帧轮询（OnUpdate）？

### 1. 设计初衷与底层哲学
初学者写 Mod 最容易犯的错误：在组件的 `OnUpdate(dt)` 里每一帧去检测玩家周围有没有怪、有没有掉血。

### 2. 为什么顶流 Mod 一律采用 `inst:ListenForEvent`？
- **CPU 性能的鸿沟**：
  - 饥荒世界同时存在数千个实体。如果 100 个实体每帧都执行距离计算和状态判断，服务器 Tick（默认 30Hz）会瞬间暴跌，导致全服掉帧。
  - 事件驱动让实体在绝大多数时间处��“休眠”状态，只有当特定事情发生时（比如被攻击 `attacked`、血量变化 `healthdelta`、穿脱装备 `equip`），相关的回调才会被精准唤醒执行一次。
- **为什么需要成对清理（ListenForEvent 与 RemoveEventCallback）？**
  - Lua 的垃圾回收（GC）依赖引用计数。如果实体 A 监听了全局 `TheWorld` 的事件，`TheWorld` 会持有实体 A 的回调函数引用；即便实体 A 在世界中被打了 `inst:Remove()`，由于全局对象依然拽着它的回调，**导致实体 A 的内存永远无法被回收，引发内存泄漏与空指针大崩溃！**

## 四、 状态机（StateGraph）为什么要用“标签解耦（StateTags）”？

### 1. 设计初衷与底层哲学
饥荒的状态机（SG）管理着角色的所有动作（攻击、被击、砍树、施法、死亡）。
- **为什么不能在代码里写 `if state == "attack" or state == "castspell" then ...`？**
  - 因为状态是无限扩展的。Mod 可以增加 100 种新的施法动作，如果原版系统用状态名判断，原版代码根本不认识 Mod 新加的状态名字。

### 2. 这种设计的精妙之处：Tag 契约
- 官方定义了一套标准的动作契约标签：
  - `busy`：角色正处于僵直后摇，拒绝移动和新指令；
  - `attack`：角色正在发起攻击，配合命中帧触发判定；
  - `pausepredict`：动作执行期间暂停客机预测，由服务端绝对同步；
  - `nosleep` / `nofreeze`：霸体阶段，免疫催眠和冰冻打断。
- **好处**：你的 Mod 在写一个高阶大招时，只需要在 SG 状态里打上 `tags = { "busy", "nosleep" }`，原版和其他 Mod 的所有冰冻、催眠、打断机制就会自动生效并识别你为“霸体且不可被打断”，**零硬编码、全面兼容！**
